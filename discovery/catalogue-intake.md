# Where the open questions come from

We screen externally maintained problem catalogues, trace a question to its first-party statement, and look for later results using its name and exact parameters. A listing is a lead. Admission requires a check that would answer the sourced question and a concrete route to running it.

## Full source index

[Search the entries and inspect source coverage](https://shunyaekam.github.io/oo-research/pipeline/indexed.html). Indexing happens before scientific screening. The worker imports catalogue rows and source statuses weekly, preserving separate records when two catalogues discuss the same question. Broader sources also carry archived records, proposals, resource links, benchmarks, and sampled arXiv leads. The physics view selects current catalogue entries with a source-reported open or partly resolved status and a physics catalogue or subject tag. Select all records to search outside this filter. Each collection documents its coverage in the index.

The scout takes individual entries from this pool as well as the recorded arXiv intake, visits the primary literature and compares exact formulations before shortlisting. A shortlist still needs an authored, source-matched verifier before it can become an investigation. The six current investigations are a subset of the index's subject matter.

When scored physics targets and registered problems are both available, two hosted slots go to the board and one to the registered physics queue. A decisive witness gets review first. A shortlisted board target with a proof attempt and a named remaining lemma can use one later slot to continue that same statement. Each attempt records its method, elapsed time and available token counts. The shared limit is one hosted request per hour.

### Pinned Lean pilot

The unattended worker runs a small portfolio of Lean tactics before hosted dispatch. Each fixed goal and tactic gets one attempt per proof-environment revision. The portfolio estimates a tactic's closure probability as (kernel successes + 1)/(observations + 2) and its runtime as (measured seconds + 3)/(observations + 1). Within each goal class, it tries the remaining tactic with the largest estimated probability per second. For independent attempts with fixed costs, comparing the two possible orders gives this rule. Tactics can overlap in practice. The estimates are provisional and cached outcomes prevent paying twice for the same trial.

The first registered goals use the planar diffusion reduction and the equal-magnitude Maxwell question. Intermediate lemmas have a separate outcome class. An upcoming board candidate still needs the board's own checks and merge. Count time, uncached input and output tokens for hosted work and report time to merge separately. The scientific comparison is accepted original targets per budget on fresh questions; replaying published helpers is a regression test.

The macOS proof environment lives under `/opt/homebrew/var/oo-research`, outside private home directories so the solver can read the public dependencies. It uses Lean 4.33.1, Formal Conjectures 9097e2f9, and Mathlib 0df444a3. With the official native toolchain in `lean-4.33.1-darwin_aarch64` and that Formal Conjectures checkout in `formal-conjectures-9097e2f9`, run `lake exe cache get` in the latter with the pinned toolchain on PATH, then `python3 -m ops.lean_loop` from the repo root. This compiles the exact reduction sources and trusted helpers. Worker sessions receive a disposable writable notebook with `./check Candidate.lean`, read-only public libraries, and the previous source checkpoint. Prior evidence stays in a file for on-demand reading. A new checked lemma can reopen its corresponding unfinished proof once. A stale board snapshot can resume existing registered research only; it does not establish current availability or credit.
